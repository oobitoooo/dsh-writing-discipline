# 设计说明

## 1. 问题定义

「防御性写作」不是文风问题，是**责任转移**：作者把判断成本推给读者，用免责、对冲、说教换取「不被指责」。它的可检测特征是稳定的——都是**元层面**的语言（谈论自己、谈论读者、谈论写作过程），而不是关于对象的陈述。

所以第一条设计约束：**规则只打元层面，不打内容层面。** 判「这段说得对不对」超出正则能力，判「这句在谈自己还是在谈对象」在能力之内。

## 2. 为什么是三级 + 动作标签

二值判定（有/无）在真实文本上不可用：学术写作的 hedging 是正当的，`我们认为` 有时是弱的正确表达。于是拆成两个正交维度：

| 维度 | 取值 | 用途 |
|---|---|---|
| `severity` | ERROR / WARN / INFO | 决定 CI 是否失败 |
| `action` | CUT / TIGHTEN / REFRAME / REVIEW | 决定人/机器该怎么动它 |

`REVIEW` 是关键：工具承认「这条可能承担正当功能，别自动删」。这把工具从「禁词替换器」变成「审稿助手」。没有 `REVIEW` 的 lint 会逼用户关掉它。

## 3. 为什么必须有密度层

单词级规则在中文上几乎不可用：`可能` 出现频率极高，单条命中全是噪音；而真正的病灶是**一条判断套三层保险**。两个补偿设计：

1. **限定词堆叠**（`可能或许`、`may potentially`）单独设 ERROR——这是形态学特征，与语境无关。
2. **段落密度**：同段 hedge ≥3 且**整段零量化数据**时升级为 ERROR。有数字的段落豁免——因为`可能降到 210 ms`是校准过的表达，不是防御。

这条豁免规则是整套判定里最重要的一个：它把「有证据的不确定」和「没证据的语气词」分开。

## 4. 为什么改写器要保守到近乎无能

自动改写文本的失败模式是不可见的：删掉一句，读者不会知道原来那里有信息。所以 `wd_rewrite` 只做**删除和收缩**，不做**生成**，并且：

- 含数字、引用、图表编号、链接（`KEEP_IF`）的句子永不删除；
- 只删「整句只承担免责/客套功能」的句子（`PURE_DEFENSIVE` 白名单式匹配，不是黑名单）；
- 每条变更都记 `before/after`，可回放。

能生成替代文本的是模型，不是正则。这里刻意不做。

## 5. 守恒锁的必要性

清掉防御性写作时最容易顺手删掉的是**限定词**——而限定词往往同时承担「科学边界」功能：

- `结果可能与X相关` → 润色成 `结果导致X`：句子里防御味没了，事实也变了。
- `仅在本实验条件下` → 删掉「仅」：读起来更硬，但结论越界了。

守恒锁用四种可机械检测的不变量兜住：

| 不变量 | 检测方式 | 级别 |
|---|---|---|
| 数字/单位/百分比 | 字面 token 集合差 | INVARIANT |
| 引用/图表/DOI/URL | 模式匹配集合差 | INVARIANT |
| 主张强度 | 成对词表（弱→强）同时发生才报 | VIOLATION |
| 否定 | 高相似度段落的否定词计数差 | INVARIANT |
| 适用边界 | 边界词在高相似度下消失 | CANDIDATE |

相似度用字符 bigram Jaccard（≥0.4 视为「同一段」），避免段落错位造成假阳性。

## 6. 插件壳为什么这么薄

`lib/index.js` 只做三件事：读输入（text/filePath）、调纯函数、渲染输出。所有逻辑在 `lib/rules.js`，原因：

- 纯函数可脱离 DSH 运行时单测（`npm test` 不需要装 DSH）；
- 规则表是数据，加规则不改代码路径；
- 插件 API 随宿主演进时，只有 30 行需要跟着改。

## 7. 扩展点

- **加规则**：往 `RULES` 追加对象，字段 `id / label / kind / severity / action / patterns / advice / demoteIn`。
- **加 profile 策略**：`PROFILES` + 规则的 `demoteIn`。
- **加文件类型**：`lib/index.js` 的 `SUPPORTED_EXT`。
- **加守恒维度**：`TOKEN_PATTERNS` 加一个模式；`CLAIM_LADDER` 加一对动词。

## 8. 不做什么

- 不调用模型判断「这句是否防御」。调用模型 = 不确定输出 = 无法进 CI。
- 不改写语义、不生成替代句。
- 不解析 docx/pdf/xlsx（那是另一层的事，交给对应 skill）。
- 不联网、不上报、不记录用户文本。

## 9. 从 `anti-defensive-writing` skill 借来的四件事（v0.2.0）

本项目的前身是一份本地 skill + 一个 140 行的 Python 扫描器。那个 version 里有四样东西是插件最初缺的，现在补进来了：

| 借用点 | 为什么值得搬 | 落地形态 |
|---|---|---|
| **前后对照表** | skill 里「病灶 / 改前 / 改后」三列比纯规则有用：模型拿到的是改写目标，不是禁令。只有禁令的 lint 会被写成「删掉这句」，删完句子结构塌了 | `EXAMPLES` 表（14 条），命中时 `✗/✓` 两行输出 |
| **`--max-warn` 阈值** | 只有 ERROR 二值判定的话，项目一开始就红，没人会开。预算制允许「先清 ERROR，再逐周压 WARN」 | `scan({maxWarn})` / `wd_scan(maxWarn)` / `wd-lint -m` |
| **可执行入口** | skill 的价值有一半在「能直接跑」：`-file/-text/-stdin/--json`，退出码 0/1/2。工具只能被模型调用时，CI 和 pre-commit 都用不上 | `bin/wd-lint.mjs`，含 `--fix`（带 `.bak`）与 `--diff` |
| **交付前自检清单** | 有 6 件事正则判不了（首句是否结论、删掉后信息量是否不变、风险是否写成 if→then）。清单是这类判断唯一的落点 | `CHECKLIST`，随 `wd_rules` 输出 |

同时从那份实现里学到一个**反例**：它的量化检测写的是 `\d+...|个|条|例`，导致「这个方案可能有效，或许更快」被判为「有量化数据」而豁免——量词必须绑定数字，不能独立成词。插件里改成 `\d+\s*(?:条|例|次|…)`。

## 10. 分工建议

插件负责**机械可判**的部分（找、删、锁），skill 负责**判断类**的部分（怎么写、怎么权衡）。两者不是替代关系：写完跑 `wd_scan`，改的时候按 `EXAMPLES` 的方向改，改完跑 `wd_conservation` 确认没伤到事实。
